How the engine is built

Mind map, target architecture, event lifecycle and prototype map for the bounded operational-risk rule engine. The engine proposes, a named human decides, and every decision lands in an append-only ledger. Source systems, routes and stores shown for production are a proposed design, not a description of any bank's estate.

Target architecture

The production shape the prototype grows into. The dashed line is the trust boundary: data crosses it inward as read-only feeds, and the only thing Trinetra writes is its own ledger.

Decisions this architecture locks in

  • The engine is a pure functionSame input, ruleset version and parameter set always give the same output. Each ledger row stores all three identifiers, so any past verdict can be replayed and checked.
  • Narrative is data, never instructionsFree text is held in quarantine and screened. Only the screen result crosses into the engine; classification uses structured fields.
  • Advisory, no write authorityTrinetra writes only to its own ledger. Posting to the GL or the loss dataset happens downstream, from approved rows.
  • Parameters are data, not codeThresholds, bands and the escalation matrix live in a parameter store with maker-checker approval. A board change needs no release.
  • Rulesets are pinned and signedA new ruleset is a new version in the registry. The engine refuses an unsigned or unknown version.
  • Append-only, hash-chainedEach row carries the hash of the previous one. A correction is a new version that names the row it supersedes.

VIEW 3

Event lifecycle

The states one loss event moves through, with the rules that move it. Two loops exist: a block sends the event back for fixes before any decision, and a correction after a decision starts a new version.
