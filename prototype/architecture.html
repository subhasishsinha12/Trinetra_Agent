Learning happens between versions, not inside one. Overrides, rejections and corrections are reviewed and folded into the next signed ruleset; nothing reclassifies an event on its own.

Decisions this architecture locks in

  • The engine is a pure functionSame input, ruleset version and parameter set always give the same output. Each ledger row stores all three identifiers, so any past verdict can be replayed and checked.
  • AI is a sidecar, never the pathThe Narrative AI reads free text and offers root causes, similar events and evidence gaps to the approver. It has no write path to the engine, the ledger or any authoritative field.
  • No write-back to CBS or GLTrinetra writes only to its own ledger. Posting to the GL or the certified dataset happens downstream, from approved rows.
  • Three outcomes at the gateApprove, override with a written reason, or reject and return for correction. Only the first two create an official record.
  • Parameters are data, not codeThresholds, bands and the escalation matrix live in a parameter store with maker-checker approval. A board change needs no release.
  • Append-only, hash-chainedEach row carries the hash of the previous one. A correction is a new version that names the row it supersedes.
  • No write-back to CBS / GL
  • Deterministic, rule-based regulatory path
  • AI only as an advisory sidecar
  • Human approval before any official record
  • Immutable decision history, append-only and versioned

VIEW 3

Event lifecycle

The states one loss event moves through, with the rules that move it. Three loops exist: a block sends the event back before it reaches the approver, a rejection returns it without creating a record, and a correction after a decision starts a new version.
